# LoRA training implementation status

This page records capability and acceptance, **not a training runbook or automated workflow**. The owner requested removal of training automation, parameter-method and start-handoff documents, not source, tests, datasets or model artifacts.

## Implementation

- Backend/MCP dataset inspection, preflight, explicit start, status, logs, cancellation and explicit smoke submission / on-demand result reconciliation.
- Recipe normalization/compiler, dataset/profile hashes, locking, argv/TOML generation, subprocess execution and logs.
- Integrated source candidate: readable names, durable duplicate serials, isolated run folders, actual-parameter Markdown/JSON, exact final validation and no-clobber publication.
- SD1.5, SDXL and Anima sd-scripts entry-point integration; arbitrary base models are not supported by this claim.
- Separate trainer and smoke-generation paths. A remote smoke image does not prove remote training.

Source: `backend/app/api/lora_train.py`, `backend/app/services/lora_training_decision.py`, `lora_training_recipe.py`, `lora_trainer.py` and `mcp-server/mcp_server/tools/lora_train.py`.

## Candidate naming and run contract

- New API/MCP preflight and Start require `output_name`, separate from dataset and recipe. Names are normalized to NFC, 1–64 characters and at most 192 UTF-8 bytes; portable filename and full-path limits apply. Chinese and interior spaces are retained. Illegal paths, device names, suffix overflow and trailing whitespace/periods are rejected without a new job or run.
- A SQLite write transaction and unique reservation constraints allocate names globally across datasets and time. First `水彩旅人` keeps its name, then `_002`, `_003`, and four-digit serials after 999. Existing legacy names and caller-supplied suffixed names occupy the same resolved-name namespace. Failed/cancelled allocations remain consumed. Serial means allocation order, never successful-training count.
- Preflight reserves nothing: it shows requested name and suffix format. `expected_output_config_hash` binds requested name to the recipe preview without changing the recipe hash definition. Start/status return `output_name`, `resolved_output_name`, `output_serial`, `run_locator` and output identity. Changed names require a fresh preview; unknown submissions still require reconciliation before retry.
- Backend creates `output/runs/<resolved-name>__<UTC>/` exclusively and binds it to the durable job. `artifacts/`, `configs/dataset.toml`, `logs/training.log`, `state/`, controlled `cache/`, `manifest.json` and UTF-8 `training-parameters.md` / `.json` belong to that run. Source images/captions stay in place. Managed output is excluded from discovery and cannot be selected as a dataset.
- Parameter files start as `queued` / `not started`. After locked dataset and component/capability revalidation, they are regenerated from the frozen effective recipe, actual launch argv and dataset TOML, then safely written/read back before spawn. Markdown and JSON share one allowlisted safe snapshot; manifest records both hashes. Failed spawn, cancellation and registration failure retain truthful phases. Unknown versions are marked unknown. Public reports explicitly mark private-path redaction; exact private argv/config stay in internal execution evidence and run configs.
- The bundled runner derives disk-cache paths from source image paths. The candidate defaults to memory caching and rejects explicit effective disk caching with `run_cache_not_isolatable`; it does not rewrite the runner or relocate datasets. Controlled library caches and temporary state use the run tree. Launcher execution remains in the existing Backend-host route; no remote trainer is added.
- Only `artifacts/<resolved-name>.safetensors` is eligible. Validate confinement/no links, nonempty safetensors structure, tensor bounds, basic LoRA pairs and SHA-256 before publication. Publish a verified copy beneath `AI-Drawing/<run-locator>/` with an ownership marker and atomic no-clobber final creation. Same-job, same-source/hash retries are idempotent; foreign/unknown/different bytes conflict. Original run files are retained.
- LoRA inventory keeps legacy root files plus one controlled `AI-Drawing/<run>/` level. Full relative locators survive API/MCP, UI selection, graph inputs and mocked smoke payloads. Ambiguous multi-root locators are excluded and reported in `lora_conflicts`. Other model scanners retain their established scope. Legacy jobs remain readable with missing allocation metadata as unknown, without automatic moves, renaming or re-registration.

Schema additions are nullable and the reservation table is additive. Compatibility is tested with a temporary legacy SQLite database only. Deployment and rollback require a separate environment-manager operation; preserve consumed reservations, old/new run files and DB backups. The candidate handoff contains detailed checks and rollback limits.

## Public status, failures and logs in the repair candidate

- Aggregate HTTP `current_job` and every queue entry carry requested/resolved names, serial, run locator and `output_config_hash` from the real service. UI primary labels use allocated names; the UI regression consumes a real FastAPI JSON response, including `_002` and `_003`.
- Start, durable job and preflight report metadata use the safe public projection. Private Unix/Windows component paths are explicitly redacted. Internal argv and dataset TOML are represented as redacted evidence with retained status/hash; the readable safe parameter files remain the report for effective options. Exact internal durable evidence and run configs are unchanged. Preflight's canonical `start_payload` remains the caller's executable input, rather than replacing component inputs with display redactions.
- Legacy records are projected too. Missing names/serial/run metadata remain unknown; public output/log paths are explicitly redacted when a run mapping is unavailable. No model, historical log, training final or registration is migrated, renamed or rewritten by reads. Explicit per-job reads may update only the smoke projection as documented below.
- Failure messages, details, recovery hints and application/run logs use a closed LoRA error vocabulary with fixed copy. Arbitrary exception messages, nested details, hints and tracebacks are never logged or echoed. Unknown exception codes become `unexpected_error` (or the operation-specific registration fallback). Safe digest/field coordinates may remain; unknown diagnostic data is omitted. Public job errors and aggregate `last_result` retain a nonempty error code plus classification, phase and recovery hint. Dataset metadata read failures and recipe preflight failures remain invalid/blocking assessments. Validation errors omit submitted values and exception context.
- New run logs contain only structured LoRA lifecycle/failure events and numeric parsed progress. Raw subprocess stdout is consumed for progress but is not copied to run/application logs or console; arbitrary trainer diagnostics may contain paths or credentials. Bounded HTTP/MCP logs reconstruct only known events and explicitly redact old unstructured lines. Existing raw legacy logs stay on disk. This is a local LoRA policy, with no global logging framework, private diagnostic service or retroactive cleanup.
- Spawn failures preserve failed/not-started truth and consumed names. Registration failures retain verified output and `registration_failed`, without success callbacks. A completion callback exception produces the safe `completion_callback_failed` event while the already registered training artifact remains completed; it is not retried automatically.
- MCP enforces its own public projection against older Backend payloads and mock HTTP: names and complete safe locators survive; private evidence and arbitrary failure strings do not. Backend and MCP keep separate component environments and add no dependency on each other.

### Legacy option and MCP diagnostic projection contract

- Public requested/effective recipe `optimizer_args` and `lr_scheduler_args` use a closed display contract in Backend and independently in MCP. Known numeric options (including signed decay rates), boolean options, beta pairs and enumerated modes retain their original readable strings when typed and bounded. Unknown keys, unknown free text, malformed option shapes and path-bearing values become `<redacted unknown or unsafe legacy option>`. Unix, Windows drive/UNC, quoting, spaces and embedded `key=value` paths receive the same treatment. This is a report projection; it does not normalize or migrate the durable recipe, argv, TOML or hashes, or rewrite preflight's executable `start_payload`.
- MCP HTTP errors, list-shaped 422 validation and HTTP-200 `ok:false` share closed diagnostic rules. Known field paths, alias/form identifiers, issue types/codes, suggestion identifiers, enum values and literal expectations survive. Free diagnostic prose and unknown identifiers are omitted, even when they look like valid identifiers. Locations allow bounded indices only on optimizer/scheduler argument and encoder-rate collections. Length limits require actual nonnegative integers up to 1,000,000; numeric bounds require finite nonnegative numbers up to 2**32, with positive `multiple_of`. Booleans are excluded from numbers, and huge integers are range-checked before float conversion. These are public diagnostic bounds, not new input/trainer limits.
- The bounded matrix covers `issues`, `validation_errors`, field/path/location/loc, accepted fields/forms/values, suggestion, constraints and validation context for both failure formats. Malformed and non-JSON bodies keep safe local error copy, code and recovery guidance, plus `classification: backend_failure` and `phase: request` for the failed MCP request. Durable job failure phases remain their separately projected job state. No raw error-body fallback is used.
- Backend and MCP remain independently deployed and tested in their own existing Python environments. Their fixed option-display vocabularies are intentionally mirrored; adding reportable options or recipe aliases requires reviewing both contracts. Unknown options continue to execute under the existing input contract where otherwise permitted; redaction does not claim their exact value was shown. No general sanitization framework or cross-component import is introduced.

The repair adds no database schema changes. Its handoff records red-to-green commands, original QA test provenance, source/tree/delta manifests, scope limits and rollback guidance. The integration handoff records current verification of the historical multi-LoRA expectations and the remaining installed Windows/filesystem limits.

## Smoke completion and recovery contract

- A newly accepted submission returns `submitted` and `artifact=None`; only subsequent reconciliation can establish a completed, retrievable image.
- `GET /api/lora-train/jobs/{job_id}` reconciles only that training job's existing `smoke_test_job_id`. Repeat `POST .../smoke-test` returns the bound job/result; changed prompt/target arguments do not create another attempt. Status/log/cancel reads never submit generation. No watcher, callback automation or new service is added.
- Queue `queued`/`running` remain pending even when partial images exist. Explicit failure/cancellation wins over partial artifacts and is preserved on the training row once observed. Completed is reported only for a nonempty, decodable, confined Gallery image recorded under the exact generation job; queue disappearance, unrelated images and completed-without-images are insufficient.
- Selection is deterministic: the lowest valid image-artifact id, then the lowest legacy image id when no generic artifact exists for that locator. Conflicting job ownership, missing/invalid files, absolute/traversal paths and symlinks are rejected. Existing record identity/provenance stays in Gallery. `smoke_test_artifact` / smoke response `artifact` are relative Gallery locators; additive artifact/image ids and an encoded `/gallery/` URL allow retrieval through existing interfaces. Status revalidates files, so disappearance returns `artifact_unavailable` and restoration can recover on refresh.
- Image validation retains structure/checksum verification and reopens the file for full pixel decoding. Known image/file failures, including PNG checksum `SyntaxError`, invalidate only that candidate, allowing the next valid image for the same job. If all candidates are invalid, status and bound repeat smoke requests return HTTP200 `artifact_unavailable` with `smoke_artifact_unavailable`, no artifact ids/URL and safe recovery guidance. Refresh also corrects a persisted false completed projection. Restoring only image bytes can recover the original job without a new submission; validation never rewrites or deletes images or changes global Pillow tolerance. Unknown programming/database errors retain their existing containment rather than being classified as invalid images.
- A compare-and-swap update prevents a stale observation from overwriting a newer binding/outcome. No public training name, serial, run locator, parameters, final hash or registration is replaced by a smoke failure. Previously observed running/completed state does not regress merely because a stale queued snapshot appears.
- One durable conditional claim precedes submission. Concurrent/repeated calls cannot both claim the same unbound smoke. `submitting` is recorded before the call; a timeout/unknown/malformed receipt becomes `submission_unknown`, without blind retry. The sole definite no-acceptance case is `QueueFullError`, which retains the existing HTTP400 contract and permits another explicit request after capacity returns. A bound failed/cancelled smoke is retained rather than resubmitted.
- Recovery states are `unknown` (missing/unrecognized job), `artifact_unavailable` (no valid image), `submitting` and `submission_unknown`. Closed `smoke_test_error_code`/`smoke_test_hint` fields (response `error_code`/`hint`) describe the action without raw queue exceptions, paths or credentials. MCP independently validates these fields and reconstructs Gallery URLs from safe relative locators.
- Durability limits: queue ordinary-job failures/cancellations are bounded in-memory evidence until a refresh persists the projection. A restart/eviction before that observation leaves `unknown`; it does not imply completion. Durable images recover after queue loss. A crash/timeout before the generation id is returned leaves an unbound claim for operator reconciliation using Backend evidence; this change adds no force-retry/reset endpoint and claims no cross-process exactly-once delivery. The existing queue itself is not made durable here.
- No schema changes or live migration. These are source/fixture guarantees; actual model loading, GPU/Windows execution, real generation, deployment and aesthetic acceptance require separate evidence and authority. The current frontend does not consume per-job smoke fields, so its product code is unchanged; its existing HTTP-name compatibility case remains applicable.

## Lifecycle observation and admission candidate

The isolated lifecycle candidate in [AID-43](/AID/issues/AID-43#document-engineering-handoff) adds the following source contract. Independent QA, integration, deployment and real training remain separate. It neither classifies historical pending jobs nor grants maintenance/data disposition authority.

`GET /api/lora-train/status` retains memory-only `status`, `current_job`, `queue` and `last_result`. Its new `durable` object independently observes nonterminal records. `availability` is `available` or `unavailable`; `nonterminal_total`, `tracked_total` and `untracked_total` are integers only when observation succeeds, otherwise null. `jobs` contains at most 50 minimal `{job_id,status,memory_tracked}` entries in binary ascending `job_id` order, with `limit`, `truncated` (null when unavailable) and `order: "job_id_asc"`. Counts include all rows outside completed/failed/cancelled; unfamiliar status values project as `unknown`. Memory membership is a snapshot of this module's queue/current job, not proof of ownership, an orphan verdict or a restart-safety decision. A concurrent worker can change membership after the snapshot.

The reader uses SELECTs against SQLite `mode=ro&immutable=1`, with a read transaction and no commit, lazy table creation, schema upgrade, smoke reconciliation or runner. Legacy stores with at least `job_id` and `status` are observable without newer columns. Missing files/tables/minimal columns, connection errors, unsupported database drivers, malformed identifiers and WAL-format databases remain unavailable. WAL and existing rollback journals are deliberately refused because readonly SQLite can touch shared-memory sidecars and immutable reads would miss uncheckpointed state. Immutable mode seals the sidecar boundary even if journal mode changes after inspection; inode/size/mtime/ctime and rollback-journal checks after the read discard results from a changed store. These checks are bounded filesystem evidence, not certification against adversarial metadata restoration or filesystem faults. There is no fallback to a false zero. In-memory SQLite uses the existing connection for tests/in-process stores. UI always displays durable pending/unknown separately, including against an older Backend without this field.

Normal Start remains HTTP 202 with the existing canonical `job_id` and response fields. If persistence returns ambiguously, a SELECT-only same-ID probe distinguishes confirmed absence (original rejection) from present/unknown (uncertain admission). After a successful durable insertion, run preparation, memory append, worker initialization or acknowledgement projection failure returns HTTP 503 with `detail.code: "admission_uncertain"`, the same `detail.job_id`, a fixed message and the fixed hint `Check the recorded canonical job_id first; do not resubmit this training request automatically.` No raw exception is public. Queued-log or informational logger failures are ancillary: they do not block worker initialization or erase acknowledgement. An uncertain newly allocated run remains preserved; its reserved name stays consumed. The implementation does not resume, retry, cancel or infer terminal disposition. Callers reconcile the recorded ID under their existing operation authority; individual job reads retain their separately documented smoke reconciliation behavior.

MCP `lora_train_start` preserves the recognized HTTP 503 code and a validated opaque ID in both top-level `job_id` and `error.job_id`, with independent fixed no-resubmission copy. UI puts these results under “提交待核對”, preserving the ID and a reconciliation instruction instead of labeling them unsubmitted failures. Earlier Backend shapes remain compatible but cannot supply a missing ID.

Tests must establish an explicit dedicated `AI_DRAWING_TEST_ROOT` under system scratch before collection. Root conftest activates all DB/output/Gallery/LoRA/publication/Prompt Library/cache/watch/model roots before importing Settings or `app.main`; the opt-in config seam skips both dotenv loaders. Missing roots, escaped paths and symlink test roots/DB/output paths fail closed. Autouse test sessions use fresh real in-memory SQLAlchemy stores unless a test supplies its own scratch DB. Production config/startup is unchanged when this test option is absent. This boundary does not make arbitrary tests safe by itself: use the guarded, secret-free runner described in README, including its filesystem, database, network and child-process controls. The existing standalone HTTP fixture uses the same bootstrap. No production lifespan is part of these offline checks.
