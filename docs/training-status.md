# LoRA training implementation status

This page records capability and acceptance, **not a training runbook or automated workflow**. The owner requested removal of training automation, parameter-method and start-handoff documents, not source, tests, datasets or model artifacts.

## Implementation

- Backend/MCP dataset inspection, preflight, explicit start, status, logs, cancellation and smoke submission.
- Recipe normalization/compiler, dataset/profile hashes, locking, argv/TOML generation, subprocess execution, logs, output discovery and registration.
- SD1.5, SDXL and Anima sd-scripts entry-point integration; arbitrary base models are not supported by this claim.
- Separate trainer and smoke-generation paths. A remote smoke image does not prove remote training.

Source: `backend/app/api/lora_train.py`, `backend/app/services/lora_training_decision.py`, `lora_training_recipe.py`, `lora_trainer.py` and `mcp-server/mcp_server/tools/lora_train.py`.

| Smoke image | Submission returns a generation job ID | ComfyUI loading, image retrieval and completed smoke state |

Canonical source gaps (the isolated candidate below does not change this worktree or an installed service):

- `submit_smoke_test` stores `submitted` and returns `artifact=None`; no training-job reconciliation of generation completion/artifacts was found.
- A job can reach completed despite a separate registration error. Consumers must distinguish training completion from registration success.
- Discovery checks file presence and can fall back to a folder prefix. Valid safetensors and unambiguous current-job attribution need acceptance verification.
- `trigger_check` only finds candidate folders; the completion callback does not generate a smoke image. The removed watcher-to-training-to-generation pipeline is not an operating procedure.

Training integration exists but is **not accepted as a complete service**. Neither “no training code” nor “fully available training” describes the evidence.
