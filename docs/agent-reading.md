# Agent reading and skill bindings

This contract controls planning/history reads, not product specifications or execution permission. Existing role, owner-delegation, independent-QA, memory, data, budget, pause and retry rules remain in force.

## Producer and equivalent coordinators

The existing Producer (Investment Lead or Reviewspec Planner where applicable) must load `project-roadmap-steering` and physically read its current installed `SKILL.md` and linked format reference before planning, selecting work or disposing of task results. Read the repository README, `docs/roadmap/ROADMAP.md` and `docs/CURRENT.md` at planning turns and task start/resume when present. Consult `docs/PROGRESS.md` only to trace relevant history; it is not a routine startup prerequisite.

When planning files are missing or incomplete, follow the skill's draft/proposal and owner-decision rules. A draft, missing approval or successful internal process is not milestone approval. Continue only work already required by existing approved authority while a blocking decision is pending. Do not manufacture threshold values or approval records.

## Workers and Auto Dreamer

Workers read their assigned task contract and its named specifications, candidate and evidence, together with existing mandatory role/project and memory-index reads. ROADMAP, CURRENT and PROGRESS are not universal worker startup requirements. Producer supplies milestone Purpose, evidence-path step, trade-off, exclusions and required inputs in the task contract.

The dedicated Auto Dreamer uses `project-memory-curation`, physically reading the installed skill and its linked format reference. It alone routinely curates the deployment's designated project-memory tree; Producer and peers remain readers and report evidence-backed candidates. Dreamer may inspect relevant planning/history as evidence without acquiring planning, dispatch or acceptance authority. Keep existing canonical memory locations and product boundaries; this publication does not migrate them.

## Repository and update boundaries

The canonical product checkout uses `main`. An explicitly assigned working branch/worktree may remain in use, carrying the same current reading contract. Preserve unrelated uncommitted work, frozen candidates and historical branches; do not switch, reset, merge or publish merely because this document names a branch. Project-workspace metadata, actual checkout branch and realized task workspace must be checked separately.

This rollout installs reading/skill bindings; it does not claim that a running conversation reloaded them, that a ROADMAP has been drafted/approved, or that product work has passed acceptance. ROADMAP/CURRENT creation and PROGRESS migration remain Producer work under the skill and applicable authority.
