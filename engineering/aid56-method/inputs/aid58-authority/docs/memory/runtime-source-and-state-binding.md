## Context

The dated AID-38 readiness snapshot found a Backend and bot consuming canonical source through tmux. The Backend had the repository-root SQLite file open, differing from the Compose default path. It had no observed reload flag, but that did not establish that writing source beneath an active process was safe. Process, listener and container visibility were bounded; queue activity and effective private settings were not inspected.

The accepted `aid36-posix-v1` kit preserves selected source bytes, numeric permissions and absences in scratch. Its inverse patch does not undo live additive schema, consumed serials, revision metadata or run/publication records. Kit acceptance and runtime/state rollback remain separate.

## Why

Setup defaults, current working directory and an interpreter path do not prove which source, dependencies or persistent files a running consumer uses. Backing up a default directory can miss actual state, and restoring old source can leave newer state exposed to older behavior.

## How to apply

Before integration, revalidate the affected consumers, actual source or mounts, ingress and writers, and observed persistent paths. Record observation time and visibility limits; keep transient PIDs, queue contents and readiness decisions in native task evidence rather than durable memory. Absence from a snapshot, an empty aggregate queue or a missing reload flag does not prove global quiescence or resolve uncertain submissions.

Resolve path aliases before classifying consumers as different checkouts. For an installed or editable Python entry, correlate realpath with the entry-point shebang, selected install metadata and inspected path configuration; a different literal prefix alone is insufficient. Keep observed import origins separate from configuration and metadata evidence.

Checkpoint plans must preserve symlinks and the state they reference. Record each link and resolved target without silently following links during a tree scan. Identify targets outside the selected checkpoint roots; targets already covered by another root must not be counted twice when estimating capacity. Metadata sizing and available space are planning evidence, not a completed consistent backup or successful restore.

Validate any proposed status route before treating it as read-only: aggregate in-memory views differ from job endpoints that may reconcile durable state. Keep private configuration and response contents private, retaining only the minimum approved projection. Validate one-shot response projections against the inspected schema before consuming the read allowance. If the projector discards the authoritative status or selects a nonexistent field, retain unknown; do not reconstruct a raw response that was not retained or silently repeat a bounded read. Any supplement must follow its actual continuation authority. This is an observer limitation, not proof of a product defect. Resolve dependency and consistent-backup prerequisites before proposing the actual maintenance operation; preserve canonical job/run IDs and newer state during recovery. Do not normalize source or overwrite current authority to satisfy an old package preimage.

Backend closure does not isolate every MCP path in this repository. The MCP Backend client uses the configured Backend API, while `tools/comfyui.py` and `tools/comfyui_nodes.py` call ComfyUI directly and `tools/discord_delivery.py` calls a separate Bot operator endpoint. Default URLs are source configuration, not live binding evidence. Name the actual supported controls, actor and covered endpoints; a no-call commitment is a caller hold, not a disconnected transport or an OS fence. If a per-server lifecycle action is unavailable, retain the precise capability gap and submit any narrower existing ingress alternative with its uncovered routes for review. Do not invent commands, kill/config workarounds or gateway restarts. Keep actual manual caller coordination separate from the exact operation grant, and retain the qualified remote-delivery hold rather than demanding remote uncertainty become zero.

Test isolation must exist before importing Settings, the database module or the application. The accepted `92e96e9` trainer tests already have an autouse `isolated_training_db` fixture that rebinds the engine and `SessionLocal` to scratch SQLite. The earlier investigation called the original test body directly, bypassing that fixture. Its committed queued row surviving a memory reset demonstrates memory/durable divergence; it does not establish that accepted normal pytest execution writes production DB. Inspect which fixtures actually ran before drawing an isolation conclusion. The root conftest's earlier import of `app.main`/Settings remained a separate pre-import gap even with that fixture, and was independently reproduced under a guard. Do not infer historical job provenance from either counterexample.

Use a verified scratch-only database/settings boundary and fail closed before imports; a worker stub or memory reset alone provides no DB isolation, and a test reset must not delete production records. The later unmerged lifecycle candidate adds explicit pre-import bootstrap and passed independent offline checks. That source verdict is not installed adoption, OS confinement or permission to run tests against live state.

SQLite read-only flags alone do not establish a consistent, side-effect-free WAL observation. The independently reviewed lifecycle reader reports WAL/journal or changing files as unavailable instead of treating an immutable main-file read as complete state. Preserve unknown rather than false zero; never ignore uncheckpointed state or create sidecars merely to obtain a count. Follow the exact task's approved reader and data scope.


Companion coverage must follow the actual implementation's complete filename construction, including hidden temporary files. In accepted `discord-bot/bot/attempt_store.py`, atomic ledger writes use `.` + ledger basename + `.` + UUID + `.tmp`, alongside owner/checkpoint files. A sibling filter using only `startswith(ledger_basename)` misses that leading-dot form. This source/string counterexample does not prove any live temporary exists or that an older Bot loaded that source; bind the implementation and preserve unknown until authorized evidence establishes the actual set.

Bot completed-delivery records suppress completed duplicates; they do not enumerate active or uncertain sends. Source-executed controls show external acceptance can precede a returned receipt, a later chunk can fail, and a ledger write can fail after sending. Blind retry, force-resend or restoring an older ledger can duplicate delivery. Preserve uncertainty and bind the effective ledger, cwd and single writer; a default path or an empty/corrupt ledger is not proof of clean history. Removing menus does not disable an existing modal callback, and a per-service lock does not establish a cross-process admission barrier.

A shutdown helper returning after a timed join is not proof of worker exit. Source/fake controls reproduced queue/history handles still alive, a scheduled caption callback after stop, and a Backend lifespan with trainer startup but no trainer-stop call. These are source-contract findings, not observations of live host work. Require a verified admission boundary and actual affected-worker/child closure; never use a cancellation or log line to manufacture zero active/uncertain work. New source gates cannot certify an older process that has not adopted them. The first-cutover legacy Bot delivery policy is now decided by Hermes under CTY delegation: retain all positively unreconciled pre-cutoff remote outcomes as unknown, keep the Bot stopped/quarantined and prohibit retry/replay, force-resend or ledger reset/old restore from releasing the hold. This refines only that legacy remote-delivery strict-zero facet. A separately authorized operation still requires proven local ingress/writer/child/FD closure, a private consistent checkpoint and isolated restore, and every unchanged exact-job/data guard. Active or uncertain generation/training and new/missing/changed nonterminal state still stop. Held outcomes require positive reconciliation or a separate exact release decision; no unknown is certified zero, and no new source/data/service operation or normal Bot startup is granted by this policy.

A ledger/checkpoint hash pair can detect a stale or inconsistent single-file restore. Restoring the whole local root coherently can also rewind that pair, so it cannot prove the absence of later remote effects. Recovery needs an externally trusted checkpoint or another explicitly authorized disposition; a locally consistent pair is not external delivery proof. The original maintenance candidate documents this limitation. Its close-receipt defect was repaired in a later unadopted candidate and passed independent source/offline retest; that repair does not change the whole-root rollback boundary.

Validate uncertainty on the actual close/drain receipt before treating it as a safe maintenance boundary. Independent handler controls found that a raw admission drain could report closed with empty uncertainty while a later persistence-aware status detected a missing/corrupt ledger or inconsistent checkpoint. Keep unreadable history as unknown/held on every relevant receipt; a later status side effect must not retroactively certify the earlier response. This is a source-level counterexample, not evidence that a live maintenance operation or remote send occurred. The repaired source obtains the close receipt through the persistence-aware projection after drain and retains a sanitized monotonic hold on unreadable history. HTTP 200 means no active work for that close response, not necessarily zero uncertainty; inspect the typed state and counts.

Current full-file copy sizes do not by themselves bound complete post-transaction or post-start state. Bind capacity assumptions to the actual protected roots, companions, schema and write set; page-rounded named-file sizes and proposed metadata/temp reservations remain estimates until their coverage and limits are justified. Do not certify a full logical/physical budget by substituting current DB size for the later full DB copy or by assigning arbitrary overhead envelopes. Missing inputs are a specific proof gap, not demonstrated disk shortage.

A failed process/client locator is unknown, even if its empty output parses into zero IDs. Retain the exit/error classification; a different utility's literal-input fixture cannot establish the failed command's cause or absence of clients. Source-only validation of a method is separate from permission to perform another live observation.

This memory grants no runtime query, private-setting, backup, service, deployment, compute or spending authority. Follow the current native task for exact operations. Windows installation/reporting remains deferred.
